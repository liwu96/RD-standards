# ADR（架构决策记录）模板

> 使用场景与判定标准见 `rules/common/development-workflow.md` §3。
> ADR 存放于业务仓库 `docs/adr/`，顺序编号：`0001-<slug>.md`、`0002-<slug>.md`。

## 什么时候值得写 ADR

三个条件同时满足才写，否则跳过：

1. **难以逆转**——事后改主意的代价很大（数据库选型、事件溯源、monorepo）
2. **没上下文会奇怪**——未来读代码的人会问"当初为什么这么做"
3. **真实权衡的结果**——存在合理备选，你因具体理由选了这一个

## 模板（正文从此处开始）

```markdown
# <决策标题>

<1~3 句话：背景是什么、决定了什么、为什么。>
```

**就这么多。** ADR 的价值在于记录"做过这个决定"和"为什么"，不是填表格。

## 可选段落（确有价值时才加）

- **Status**：`proposed | accepted | deprecated | superseded by ADR-NNNN` —— 决策会被重新讨论时使用
- **备选方案**：被否掉的替代方案值得被记住时（否则半年后有人会再提议一次）
- **后果**：不明显的下游影响（性能代价、运维负担、锁定）

## 典型合格主题

- 架构形态："订单写入走事件溯源，读模型投影到 MySQL"
- 上下文间集成："订单与账务通过领域事件交互，不用同步 HTTP"
- 有锁定效应的技术选型：数据库、消息中间件、认证方案、部署形态
- 边界与归属："客户数据只归客户域，其他域仅按 ID 引用"（明确的"不"与"是"同样有价值）
- 刻意偏离常规："此处手写 SQL 不用 ORM，因为 X"——防止下一个人把它"修好"
- 代码里看不见的约束："因合规要求不能使用 XX 云"；"因合作方契约，响应必须 <200ms"
