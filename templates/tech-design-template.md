# 技术方案模板

> 使用场景与卡点见 `rules/common/development-workflow.md` §3。
> 填写原则：每节服务于"评审人能否据此判断方案正确性与风险"；无内容的节保留标题并写"无"。

```markdown
# 技术方案：<需求/项目名>

- 作者 / 日期 / 评审人：
- 关联需求（链接/编号）：
- 变更等级：新服务 | 模块级改动 | 公共库改动 | 仅业务逻辑

## 1. 背景与目标
<解决什么问题，成功标准（可量化）>

## 2. 方案概述
<核心思路 3~5 句话 + 一张关键流程/时序图（mermaid 或图片）>

## 3. 详细设计
### 3.1 接口设计
<新增/变更的 API 列表；走完 skills/rd/api-design 后粘贴结论（URL、出入参、错误码）>

### 3.2 数据库设计
<新表/改表/索引；粘贴 db-schema-review 结论（含建表 SQL）；
数据量预估（3 年）、是否分表、归档策略>

### 3.3 三方依赖
<新接入的三方服务/库；粘贴 third-party-integration 评审结论（五件套配置）>

### 3.4 核心 logic
<状态机、并发/幂等处理、事务边界（哪些操作同一事务）、失败补偿>

## 4. 非功能设计
- 性能：预估 QPS/P99，压测计划
- 容量：存储/内存/连接数预估
- 降级与熔断：依赖故障时的行为
- 兼容：新老版本并存策略、数据回填方案

## 5. 上线计划
- 发布顺序（DDL → 代码 → 配置/开关）
- 灰度步骤与观察指标
- 回滚方案（每一步分别怎么回）

## 6. 测试计划
<单测范围、集成/E2E 场景、预发验证项>

## 7. 风险与待定项
<开放问题、需要评审拍板的点>

## 8. 决策记录
<满足 ADR 条件的决策，另写入 docs/adr/ 并在此引用编号>
```

## 评审人自查（收到方案后）

- [ ] 接口/数据库/三方三块是否都过了对应 skill 的清单
- [ ] 事务边界与失败补偿是否说清（对应数据库规范 §6）
- [ ] 回滚方案是否每步都可执行（不是"回滚代码"四个字）
- [ ] 数据量与容量预估是否做了（不是"后面再说"）
