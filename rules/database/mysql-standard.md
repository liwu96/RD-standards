# MySQL 数据库设计与使用规范

> 依据（源材料见 `references/`）：
> - 《阿里巴巴 Java 开发手册》1.3.0·MySQL 数据库章节（建表/索引/SQL/ORM）
> - 阿里云开发者社区《企业级 MySQL 数据库设计与开发规范》
> - 腾讯云开发者社区《绝对必备：MySQL 数据库开发的完整规范指南》
> - 《MySQL 实战 45 讲》全部 45 讲消化笔记（`references/mysql-45-notes-*.md`）
>
> 约束级别：【强制】/【推荐】/【参考】。多来源冲突时从严执行并在条目后标注出处。

## 1. 命名规范

1. 【强制】库名、表名、字段名一律小写字母 + 数字 + 下划线，禁止大写字母、禁止数字开头、禁止两个下划线间只有数字（Linux 下大小写敏感，Windows 不敏感，跨环境移植会出问题）。正例：`aliyun_admin`、`level3_name`；反例：`AliyunAdmin`、`level_3_name`。【手册】
2. 【强制】禁止使用 MySQL 保留字（`desc`、`range`、`match`、`delayed` 等）。【手册/阿里云】
3. 【强制】表名不使用复数名词；命名做到见名知义，不超过 32 个字符；推荐"业务名称_表的作用"（`trade_config`、`force_project`）。【手册/阿里云】
4. 【强制】库名与应用名称尽量一致；程序连接不同库使用不同账号，禁止跨库 join，为分库分表与权限最小化留余地。【手册/阿里云】
5. 【强制】临时表以 `tmp_` 前缀 + 日期后缀；备份表以 `bak_` 前缀 + 日期（时间戳）后缀。【阿里云/腾讯云】
6. 【强制】索引命名：主键 `pk_字段名`、唯一索引 `uk_字段名`、普通索引 `idx_字段名`。【手册】
7. 【强制】表达"是否"概念的字段用 `is_xxx`，类型 `unsigned tinyint`（1 是 / 0 否），如 `is_deleted`。【手册】
8. 【强制】存储相同数据的列，列名与列类型必须完全一致（尤其关联列：类型不一致会隐式转换导致索引失效）。【阿里云】
9. 【强制】SQL 关键字统一大写（团队内统一即可），库名表名字段名小写。【腾讯云】
10. 【强制】禁止在数据库中存储明文密码。【腾讯云/安全】

## 2. 建表规范

1. 【强制】存储引擎统一 InnoDB；禁用 Memory 引擎（重启丢数据、备库重启中断同步）；使用其他引擎需 DBA 审批。【阿里云/腾讯云/45讲】
2. 【强制】字符集统一 `utf8mb4`（兼容 emoji，避免隐式转换导致索引失效；各表、各列、连接字符集必须一致）。【腾讯云/45讲，从 utf8 与 utf8mb4 两源中取 utf8mb4】
3. 【强制】每张表必须有显式主键：`id bigint unsigned NOT NULL AUTO_INCREMENT`。
   - InnoDB 是索引组织表，无主键的表使用全局 row_id（6 字节），到 2^48 归零会**静默覆盖旧数据**；且无主键/无唯一键的表会使备库并行复制退化为单线程。【45讲】
   - 禁止 UUID、MD5、HASH、字符串列做主键（无法保证顺序增长，页分裂开销大）；不用更新频繁的列、不用多列联合主键。【阿里云/腾讯云】
   - int 上限约 42.9 亿行，高频写入表直接用 `bigint unsigned`。【45讲】
4. 【强制】表必备三字段：`id`、`gmt_create`、`gmt_modified`（datetime，程序在插入/更新时维护；更新记录必须同时更新 `gmt_modified`）。【手册/ORM】
5. 【强制】所有表和字段必须加 comment，从建表起维护数据字典；字段含义或状态追加时同步更新注释。【阿里云/腾讯云/手册】
6. 【强制】禁用外键与级联（`foreign key`），一切外键概念在应用层解决。外键/级联适合单机低并发，分布式高并发下是更新风暴与死锁来源，且影响备库并行复制。【手册/腾讯云/45讲】
7. 【强制】禁止在表中建立预留字段（命名无法见名识义、类型无法确定、修改类型会锁表）。【阿里云】
8. 【强制】禁止在数据库中存储图片、文件等大二进制数据；文件放对象存储，库内只存地址。【阿里云/腾讯云】
9. 【推荐】单表数据量控制在 500 万行以内或单表容量 2GB 以内；超过再分库分表（日志类可历史归档）。三年内达不到该量级的表，建表时不要预先分表。【阿里云/手册】
10. 【推荐】单表过大时优先业务分表/分库分表，**不使用分区表**（分区表共用整表 MDL 锁、首次访问需打开所有分区）；确需按时间分区管理的，控制分区数量并按时维护。【45讲/阿里云（取 45 讲结论）】
11. 【推荐】冷热数据分离、减小表宽度：经常一起使用的列放同一张表，大字段（text/blob）拆到扩展表用主键关联，提高缓冲池命中率。【阿里云】
12. 【强制】禁止从开发/测试环境直连生产数据库；禁止在线上库做压力测试。【阿里云】

## 3. 字段设计规范

1. 【强制】优先选择满足存储需求的最小数据类型；非负数值加 `UNSIGNED`（无符号多一倍表示范围，并防误存负数）。【阿里云/手册】
2. 【强制】小数（金额）用 `decimal`，禁止 `float`/`double`（精度损失）；超过 decimal 范围时拆整数+小数分开存。【手册/阿里云】
3. 【强制】时间用 `datetime`（8 字节），不用 `timestamp`（2038 上限）；禁止用字符串存日期（无法用日期函数计算、占用更多空间）。统一存储时区约定（推荐 UTC 或明确 +08:00）。【腾讯云/45讲，两源冲突取 datetime】
4. 【强制】`varchar` 长度不超过 5000；更长的用 `text` 并拆独立扩展表（text/blob 使内存临时表失效、必须二次查询、只能建前缀索引、不能有默认值）。【手册/阿里云】
5. 【强制】长度几乎相等的字符串用 `char` 定长（如 MD5、国家码）。【手册】
6. 【推荐】尽可能 `NOT NULL` 并给默认值：NULL 列需要额外存储、比较计算需特殊处理、`count(col)` 语义偏差；字符串默认 `''`、数字默认 `0`。【阿里云/腾讯云】
7. 【推荐】用 `tinyint` 代替 `ENUM`（改枚举值要 ALTER、排序低效、禁止用数字做枚举值）。【腾讯云/阿里云】
8. 【参考】IP 地址可用 `int unsigned` + `inet_aton/inet_ntoa` 转换存储，节省空间。【阿里云】
9. 【参考】同一意义的字段在各表中的定义必须相同（类型、unsigned、字符集）。【腾讯云】
10. 【推荐】字段允许适度冗余以提高查询性能，但必须：不是频繁修改的字段、不是超长 varchar/text，并考虑一致性。【手册】

## 4. 索引设计规范

1. 【强制】业务上具有唯一特性的字段（含组合字段）必须建唯一索引——应用层校验挡不住并发脏数据（墨菲定律）；唯一索引对插入速度的损耗可忽略。【手册】
   - 补充（45 讲）：唯一索引用不上 change buffer，写入密集且唯一性已由业务充分保证的归档场景可降级普通索引；**业务主路径默认仍建唯一索引**。
2. 【强制】单张表索引数量不超过 5 个；联合索引字段不超过 5 个（阿里云/腾讯云一致）。索引是写代价，禁止"预防性"堆索引、禁止每列单独建索引。【阿里云/腾讯云/45讲】
3. 【强制】禁止冗余/重复索引：`primary key(id)` + `index(id)` 重复；`index(a,b,c)` 存在时不建 `index(a,b)`、`index(a)`——按最左前缀复用。【阿里云/45讲】
4. 【强制】联合索引区分度最高的列放最左侧（区分度 = `count(distinct col)/count(*)`）；存在等值与范围混合条件时，**等号条件的列前置**（如 `where a>? and b=?` 建索引 `(b,a)`）。【阿里云/手册】
5. 【强制】`varchar` 列建索引必须指定前缀长度，用 `count(distinct left(列, n))/count(*)` 评估区分度（20 字符通常可达 90%+）；前缀索引用不上覆盖索引，需要覆盖索引的场景建全字段索引。【手册/45讲】
6. 【强制】页面搜索严禁左模糊 `like '%xxx'` 与全模糊 `like '%xxx%'`（B+ 树最左前缀失效），需要全文检索走搜索引擎或 MySQL 全文索引。【手册/阿里云】
7. 【强制】防止字段类型隐式转换导致索引失效：字符串列等值条件必须带引号（`where id='111'` 中 id 为整型时索引失效）；关联两表字符集必须一致。【手册/阿里云/45讲】
8. 【强制】`where` 条件中禁止对列使用函数或运算（`month(t)=7`、`id+1=10` 均索引失效），改写为范围或常量折叠。【阿里云/45讲】
9. 【推荐】利用索引有序性消灭 `Using filesort`：`where a=? and b=? order by c` 建联合索引 `(a,b,c)`；范围条件之后的列无法参与排序（`where a>10 order by b` 用不上 `a_b` 的顺序）。【手册/45讲】
10. 【推荐】高频查询优先设计覆盖索引（查询字段全部落在索引中，`explain` Extra 为 `Using index`），避免回表；典型"按 A 查 B"建 `(A,B)`。【手册/45讲】
11. 【推荐】深分页用延迟关联优化：`select a.* from t a, (select id from t where ... limit 100000,20) b where a.id=b.id`，或限制可翻页总数/改游标分页。【手册】
12. 【推荐】`explain` 目标：type 至少 `range`、要求 `ref`、最好 `consts`；`type=index`（索引全扫描）视为待优化。新 SQL 上线前必须 explain，重点检查 Extra 中的 `Using filesort / Using temporary / Block Nested Loop`。【手册/45讲】
13. 【推荐】join 的关联字段必须有索引且类型绝对一致；被驱动表无索引的低频复杂 join，可先过滤入带索引的临时表再 join。【手册/45讲】
14. 【参考】区分度低但更新频繁的列不建索引；`order by rand()` 禁止（全表装内存排序），随机取行用 `max(id)-min(id)` + `rand()` 定位或 `count(*)+limit Y,1`。【45讲】

## 5. SQL 编写规范

1. 【强制】禁止 `select *`，明确字段列表（多耗 CPU/IO/带宽、无法用覆盖索引、表结构变更引起 resultMap 不一致）。【手册/阿里云/腾讯云】
2. 【强制】insert 必须带字段列表：`insert into t(c1,c2) values(...)`；批量插入用 bulk values 多值写法。【阿里云/腾讯云】
3. 【强制】统计行数用 `count(*)`（SQL92 标准，含 NULL 行）；注意 `count(distinct col1,col2)` 任一列全 NULL 返回 0；`sum()` 可能返回 NULL 引发 NPE，用 `IFNULL(sum(g),0)`。【手册/45讲】
4. 【强制】判 NULL 用 `ISNULL()`；`NULL<>NULL`、`NULL=1` 结果都是 NULL 不是 true。【手册】
5. 【强制】分页逻辑先 `count`，为 0 直接返回，不再执行分页语句。【手册】
6. 【强制】禁止使用存储过程、触发器、事件（难调试、难扩展、无移植性）；存储过程内禁用 `CHECK/LOCK/LOAD DATA/OPTIMIZE` 与预处理语句。【手册/腾讯云】
7. 【强制】数据订正（update/delete）先 `select` 确认影响范围再执行。【手册】
8. 【强制】`delete`/`update` 必须带 where 且 where 条件能走索引（无索引的当前读会给全表所有行与间隙加锁，等价锁全表）。【45讲/腾讯云】
9. 【强制】`truncate table` 禁止在业务代码中使用（无事务、不触发 trigger、无法闪回）。【手册/45讲】
10. 【推荐】`in` 集合控制在 500 个以内（手册上限 1000、阿里云 500、腾讯云 200——团队取 500），超限分批或改 `join`/`exists`；同一列的多个 `or` 改用 `in`。【三源折中/阿里云】
11. 【推荐】超过 3 张表禁止 join（手册强制）；MySQL 虽支持 61 张，团队按手册上限 3 张执行，超过的在应用层拆分。【手册（从严）】
12. 【推荐】明显无重复结果时用 `union all` 而非 `union`（union 要临时表去重）；`group by` 不需要排序时显式 `order by null`。【阿里云/45讲】
13. 【推荐】避免在 MySQL 端做复杂计算：大 SQL 拆小 SQL（一个 SQL 只用一个 CPU），合并同库多次往返为批量；减少与数据库的交互次数。【阿里云】
14. 【推荐】子查询优先改写为 join（子查询结果集进临时表无索引）；`not in` 用 `left join`/`not exists` 优化。【阿里云/腾讯云】
15. 【推荐】`order by` 查询只 select 需要的字段（行越短越可能走全字段排序，少触发临时文件）。【45讲】
16. 【推荐】不需要排序的 group by 尽量走索引（目标 explain 无 `Using temporary/Using filesort`）。【45讲】
17. 【参考】临时中间结果一律 `create temporary table`（session 隔离、自动回收），禁止用普通表充当临时表。【45讲】

## 6. 事务与锁规范

1. 【强制】应用侧统一 `autocommit=1` + 显式 `begin`/`commit` 管理事务（注意确认框架默认值，避免框架隐式开启长事务）；只读查询禁止显式 `begin`/`start transaction`。【45讲/腾讯云】
2. 【强制】事务尽量短小：事务内禁止 RPC 调用、文件 IO、发消息等耗时操作；杜绝大事务（单事务更新控制在万行以内）。【45讲/腾讯云/阿里云】
3. 【强制】"先 select 校验再 update"防不住并发（普通 select 是快照读）——要以读定写必须 `select ... for update`（当前读）。【45讲】
4. 【强制】事务更新多行时，把最热的行（被并发更新的共享行）的更新放在**事务最后**（两阶段锁：行锁提交时才释放）。【45讲】
5. 【强制】避免死锁第一法则：所有事务按相同顺序访问同一组资源（统一排序方向、按主键排序后批量处理）。【45讲】
6. 【强制】并发场景下的死锁/锁等待超时，调用方必须实现统一重试（保持 `innodb_deadlock_detect=on` 默认值，不靠调小 `innodb_lock_wait_timeout` 解决）。【45讲】
7. 【强制】并发插入唯一键场景必须做死锁重试（insert 唯一键冲突会加共享 next-key lock，三事务并发冲突且先到者回滚是高发死锁形态）；冲突报错后尽快 commit/rollback，勿持锁挂起。【45讲】
8. 【强制】批量删除/更新：单连接循环小批量 `delete ... limit 500`；禁止一条大语句（锁久 + 主从延迟），禁止多连接并发删（人为制造死锁）。【45讲/阿里云】
9. 【强制】隔离级别团队默认 `RR`（READ-COMMITTED 需说明"业务不需要可重复读"的理由并经评审，RC + binlog=row 是低锁冲突合法组合）。【45讲】
10. 【推荐】超 100 万行的批量写（update/delete/insert）必须分批多次执行；大批量写会造成主从延迟、row 格式 binlog 膨胀、大事务锁表。【阿里云】
11. 【推荐】并发更新同一行（账户余额等）冲突极高时：热点行拆多行、或更新请求进内存排队，防死锁检测 O(n²) 打满 CPU。【45讲】
12. 【推荐】长事务监控阈值 60 秒告警；`information_schema.innodb_trx` 巡检。【45讲】
13. 【参考】业务不得假设自增 id 连续（唯一键冲突、事务回滚、批量申请翻倍都会产生空洞）；需要连续单号用独立发号器。【45讲】

## 7. 变更与大表 DDL

1. 【强制】线上 DDL 三步走：先查 `information_schema.innodb_trx` 处理长事务 → 低峰期执行 → 尽量使用 `ALTER TABLE ... NOWAIT/WAIT n`，拿不到 MDL 锁立即放弃重试（DDL 被阻塞会连带阻塞后续所有查询，小表加字段也可能打满整库连接）。【45讲】
2. 【强制】大表（百万行以上）变更表结构使用 `gh-ost` 或 `pt-online-schema-change`，避免锁表与主从延迟。【腾讯云/阿里云】
3. 【强制】删表流程：先改名（加 `_to_be_deleted` 后缀）观察一段时间，再通过管理系统删除——`drop`/`truncate` 无法闪回。【45讲】
4. 【强制】binlog 格式必须为 `row`（`binlog_row_image=FULL`），这是主备一致性与误删恢复的共同前提；生产保持"双 1"（`sync_binlog=1`、`innodb_flush_log_at_trx_commit=1`），修改由 DBA 评估。【45讲】
5. 【强制】线上账号会话设置 `sql_safe_updates=on` 兜底（无 where 的 update/delete 直接拒绝）。【45讲】
6. 【推荐】增删改频繁、存在空洞的表，低峰期 `alter table t engine=InnoDB` 重建回收空间；线上大表用 gh-ost。【45讲】
7. 【参考】误删恢复依赖：全量备份 + binlog 保留周期按恢复窗口设定；核心库建议延迟复制备库（如 1 小时）。【45讲】

## 8. 高可用与读写分离

1. 【强制】读写分离下"写后立即读"必须拿到最新结果的请求强制走主库（或等待 GTID 再查从库、超时降级主库）；代码需显式标注每个读请求是否容忍过期读。【45讲】
2. 【强制】应用必须实现连接断开自动重连 + 幂等重试（服务端 kill 连接后表现为"一直没恢复"）；写请求收到"执行异常"先查状态再决定重试，禁止盲目重发。【45讲】
3. 【推荐】主备延迟监控 `seconds_behind_master`；45 度直线上升典型原因是备库大事务/长事务堵 DDL。【45讲】
4. 【推荐】应用连接一律走连接池（长连接），连接池空闲回收时间必须小于 MySQL `wait_timeout`（默认 8 小时）。【45讲】
5. 【推荐】禁止依赖 MySQL 查询缓存做性能优化（表更新即全清，8.0 已移除）；缓存放应用层或 Redis。【45讲】
6. 【推荐】应用侧对 MySQL 的慢查询配置告警；上线前用 `long_query_time=0` 在预发全量回归慢日志（坏查询不一定是慢查询，看 `Rows_examined`）。【45讲】

## 9. 权限与安全

1. 【强制】程序账号权限最小化：只授予所需库的 DML，不给 `drop`/`truncate`/`super`；`super` 只留给 DBA 应急账号。【阿里云/45讲】
2. 【强制】权限变更只走 `grant`/`revoke`（之后无需 `flush privileges`），禁止直接 DML 权限表。【45讲】
3. 【强制】SQL 必须参数绑定（Java `#{}`、Python 参数化），禁止字符串拼接 SQL（SQL 注入）。【手册/安全】
4. 【强制】禁止为程序账号开启 `skip-grant-tables` 等应急配置；应急手段（`sql_log_bin=off` 等）由 DBA 执行。【45讲】

## 10. ORM 使用规范（Java MyBatis / Python SQLAlchemy）

1. 【强制】表查询禁止 `select *`，字段明确写明并与 resultMap 映射一致。【手册】
2. 【强制】POJO 布尔属性不加 `is`、数据库字段加 `is_`，在 resultMap/pydantic Schema 中显式映射。【手册】
3. 【强制】MyBatis 参数一律 `#{}`，禁止 `${}`（SQL 注入）；`${}` 仅限 orderBy 列名白名单拼接场景且有注释说明。【手册】
4. 【强制】不允许直接拿 `HashMap`/`Hashtable`/裸 `dict` 作为查询结果集输出（类型不可控）。【手册】
5. 【强制】更新记录必须同时更新 `gmt_modified`；禁止大而全的 update 接口——只更新有改动的字段（易错、低效、膨胀 binlog）。【手册】
6. 【推荐】`@Transactional` 不滥用（影响 QPS），并考虑缓存、消息、搜索的配套回滚方案。【手册】
7. 【推荐】`insert ... on duplicate key update` 的 affected rows（0/1/2）不作为业务判断依据；多唯一键冲突时只改第一个冲突行。【45讲】
