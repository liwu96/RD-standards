# API 出入参规范

> 适用范围：团队所有 HTTP API 的请求与响应设计。RPC（Dubbo/gRPC）参照执行，gRPC 以 proto 定义为准。
> 约束级别：【强制】/【推荐】/【参考】，与《阿里巴巴 Java 开发手册》一致。

## 1. 请求（Request）

### 1.1 Header

- 【强制】`Content-Type: application/json; charset=utf-8`（文件上传除外，使用 `multipart/form-data`）。
- 【强制】鉴权头使用 `Authorization: Bearer <token>`；签名场景的 app key 等业务头统一加 `X-` 前缀。
- 【推荐】调用方生成 `X-Request-Id`（UUID），服务端未收到时自行生成并原样回传，用于全链路追踪。`requestId` 只用于关联一次请求及其日志，不承担写请求去重；重试可以有新的 `requestId`。
- 【强制】禁止在 URL query 中传递 token、密码、手机号等敏感信息（会被网关/访问日志留存）。

### 1.2 Body 字段

- 【强制】字段命名 `lowerCamelCase`，见《API 命名规范》§6 命名矩阵。
- 【强制】每个接口的入参必须在接口文档中标注：必填/可选、类型、长度或取值范围、示例值。
- 【强制】服务端必须做入参校验（Java 用 JSR-303/Bean Validation，Python 用 pydantic），禁止信任任何外部输入：
  - 字符串长度、数值范围、枚举合法性；
  - 分页参数 `pageSize` 上限 100，防止一次拉全量打爆内存；
  - 排序字段白名单校验，禁止直接拼接 `order by`（SQL 注入）。
- 【强制】写操作接口必须考虑幂等：支持客户端传入 `Idempotency-Key` 请求头，或请求体中的 `idempotencyKey`。客户端对同一业务操作重试时复用同一 key；服务端按接口、调用方和 key 的约定范围保存结果并去重。`requestId`/`X-Request-Id` 是链路追踪标识，不能替代幂等 key。
- 【推荐】入参对象超过 5 个字段的，定义为独立 DTO/Schema 对象，禁止用 `Map`/`dict` 裸传（对应 Java 手册"超过 2 个参数的查询封装，禁止使用 Map 传输"）。

### 1.3 分页与过滤

- 【强制】分页请求：`page`（≥1）+ `pageSize`（1~100，默认 20）；响应必须回显这两个字段与 `total`。
- 【参考】数据量超大或实时性要求高的列表（消息流、账单流水）推荐游标分页 `cursor` + `limit`，避免深分页性能问题。

## 2. 响应（Response）

### 2.1 统一响应包（Envelope）

【强制】所有接口返回统一结构，HTTP 状态码表达协议层结果，业务结果由 `code` 表达（见《状态码与错误码规范》）：

```json
{
  "code": "0",
  "message": "success",
  "data": { },
  "requestId": "c0a80121-1730-4b1c-0001-6f96b2c4e2a0",
  "serverTime": "2026-10-05T12:30:00+08:00"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| code | string | 业务状态码，`"0"` 成功，非 `"0"` 见错误码枚举（A/B/C 五位错误码） |
| message | string | 面向调用方的提示信息；错误场景给出**可读、可行动**的描述，禁止直接输出堆栈/内部异常类名 |
| data | object/null | 业务数据；成功无数据和一般失败返回 `null`；A0100 参数校验失败可用 `data.details` 返回字段级错误 |
| requestId | string | 链路追踪 ID，与请求头 `X-Request-Id` 对应；仅用于关联本次请求，不用于幂等去重 |
| serverTime | string | 服务端时间，RFC 3339 格式 |

- 【强制】失败场景不得返回半成功业务数据；一般失败 `data` 为 `null`，A0100 参数校验失败允许仅返回 `data.details` 字段级错误列表。

### 2.2 列表响应

【强制】列表数据统一包装为：

```json
{
  "code": "0",
  "message": "success",
  "data": {
    "total": 137,
    "page": 2,
    "pageSize": 20,
    "list": [ { "orderId": "10001", "orderStatus": "PAID" } ]
  }
}
```

### 2.3 字段设计

- 【强制】字段命名遵循命名矩阵（协议 `lowerCamelCase`，由框架与数据库 `snake_case` 映射），新增字段只增不改不删；确需废弃时先标记 `deprecated` 并公告，两个版本后移除。
- 【强制】对外字段类型稳定：ID 用 string、金额用整数（分）、时间用 RFC 3339 字符串、布尔用 true/false、枚举用全大写字符串。
- 【强制】敏感字段（手机号、身份证、邮箱）出参必须脱敏：`158****9119`（对应《阿里巴巴 Java 开发手册》安全规约）。
- 【推荐】列表接口只返回前端展示所需字段，明细字段走详情接口，避免大对象传输与 `select *`。

## 3. 版本与兼容

- 【强制】不兼容变更（删字段、改语义、改类型）必须升 URL 版本 `/api/v2/...`；新增可选字段视为兼容变更。
- 【强制】接口变更必须同步更新接口文档（OpenAPI/Swagger 或团队文档平台），文档与代码不一致视为缺陷。
- 【参考】提供契约测试（Pact 等）保障服务间接口兼容。

## 4. 异常与错误返回

- 【强制】业务异常返回统一 envelope + 对应错误码，HTTP 状态码按下表（详见《状态码与错误码规范》）：

| 场景 | HTTP | code 示例 |
|---|---|---|
| 成功 | 200 | 0 |
| 参数校验失败 | 400 | A0100 |
| 未登录 / token 失效 | 401 | A0200 |
| 无权限 | 403 | A0300 |
| 资源不存在 | 404 | A0400 |
| 资源冲突（重复创建、版本冲突） | 409 | A0500 |
| 触发限流 / 风控 | 429 | A0700 |
| 服务内部错误 | 500 | B0001 |
| 下游三方服务错误 | 502 | C0100 |
| 服务不可用（维护/熔断） | 503 | B0201 |

- 【强制】禁止用 HTTP 200 + 业务错误码之外的自造组合（如 200 + `status:"fail"`），团队只维护一套状态码体系。
- 【强制】message 不暴露内部细节：禁止出现表名、SQL、类名、堆栈、内网 IP；这些信息只进日志。
