# 研发工作流规范

> 适用范围：从需求到上线的完整研发过程。定义各阶段的产出物与卡点。

## 1. 流程总览

```
需求评审 → 技术方案（含 ADR）→ 开发（TDD）→ CR → 测试 → 发布（灰度）→ 观测 → 复盘
```

## 2. 需求评审

- 【强制】需求有明确的验收标准（可测试的表述），模糊需求退回产品补充
- 【推荐】开发参与需求评审，识别技术风险与隐性成本（数据量、并发、兼容）

## 3. 技术方案

- 【强制】以下场景必须先出技术方案并评审，禁止直接写码：
  - 新服务/新模块；公共库或二方库改动
  - 涉及数据库设计、分库分表、数据迁移
  - 接入新三方服务或中间件
  - 预估工作量 >5 人日的功能
- 【强制】技术方案使用 `templates/tech-design-template.md`，数据库/三方部分分别走 `skills/rd/db-schema-review`、`skills/rd/third-party-integration` 的清单
- 【强制】难以逆转且需要上下文才能理解的决策记录 ADR（`templates/adr-template.md`，存放在业务仓库 `docs/adr/`）

## 4. 开发阶段

- 【推荐】先查复用再写新代码：团队内已有组件/公共库 → 成熟三方库 → 最后才是自研
- 【推荐】新功能与 bug 修复走 TDD（见 `rules/common/testing.md` §4）
- 【强制】开发过程遵守各领域规范（`rules/api|database|java|python`）与提交规范（`rules/common/git-workflow.md`）
- 【推荐】大任务拆分为可独立评审与回滚的小步提交

## 5. 测试与发布

- 【强制】提测前完成自测 + 单测；提测单包含影响面与测试建议
- 【强制】发布走灰度：小流量 → 观察（错误率、延迟、业务指标）→ 全量；每步有回滚方案
- 【强制】发布窗口避开业务高峰；重大变更双人值守（一人操作一人核对）
- 【强制】数据库变更先于代码发布（兼容两版代码的 schema），顺序：加列 → 发代码 → 数据回填 → 清理
- 【推荐】发布后 30 分钟内重点观测核心指标，异常即回滚（回滚优先于定位）

## 6. 复盘（Postmortem）

【强制】线上事故（P1/P2 级）48 小时内出复盘报告，包含：

1. 时间线（发现 → 止血 → 恢复 → 根因确认）
2. 影响面（用户数、订单量、资损）
3. 根因（技术根因 + 流程根因，用 5 Why 追到可执行层）
4. 行动项（整改项 + 责任人 + 截止时间，逐条进跟踪表）
5. 规范增补：需要沉淀为规范/检查项/Skill 步骤的内容，提 PR 进本仓库

## 7. 文档与知识沉淀

- 【推荐】接口文档随代码同步更新（OpenAPI），契约测试保障兼容
- 【推荐】排障经验沉淀为 runbook（服务仓库 `docs/runbook.md`：常见告警、排查步骤、应急操作）
- 【推荐】每季度回顾本规范仓库：失效条目修订、新实践增补（流程见 `CONTRIBUTING.md`）
