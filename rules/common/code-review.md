# 代码评审（CR）规范

> 适用范围：团队所有代码仓库的评审流程与标准。语言专项清单见 `skills/rd/backend-cr`，本文件定义流程与通用标准。

## 1. 评审时机

【强制】以下情况必须评审，禁止绕过：

- 合并到共享分支（`main`/`release/*`）之前
- 安全敏感代码：鉴权、支付、用户数据、权限、加密
- 架构变更：分层调整、公共库/二方库改动、中间件接入
- 数据库变更：表结构、索引、数据订正脚本

## 2. 评审前置条件（请求评审前自查）

- [ ] CI 全绿：构建、静态检查（Java P3C/SpotBugs；Python ruff/mypy）、单测
- [ ] 无冲突、已 rebase 到目标分支最新
- [ ] 自查过一遍 diff（不做"甩给评审人"式提交）
- [ ] MR 描述完整（见 `rules/common/git-workflow.md` §3）

## 3. 严重级别与处置

| 级别 | 含义 | 处置 |
|---|---|---|
| BLOCKER | 安全漏洞 / 资损 / 数据错误 / 线上事故风险 | 必须修复才能合入 |
| HIGH | 高概率故障、严重性能问题 | 应当修复后合入；特殊情况登记 tech-debt 并限期 |
| MEDIUM | 违反【强制】规范但不直接出事故 | 修复或说明豁免理由 |
| LOW | 建议与风格 | 自行决定 |

## 4. 通用质量标准

- 函数聚焦（≤50 行）、文件内聚（≤800 行）、嵌套 ≤4 层（卫语句/早返回）
- 错误显式处理，无静默吞异常；无残留调试代码（print/System.out/注释掉的代码块）
- 命名可读、无魔法值；新功能有测试且覆盖达标（见 `rules/common/testing.md`）
- 性能：无 N+1 查询、列表有分页、查询有上限、昂贵计算有缓存考量

## 5. 评审流程

```
1. 看 MR 描述与关联需求，理解意图（不孤立看 diff）
2. 先过安全清单（见 rules/common/security.md）
3. 再过质量清单与语言专项（skills/rd/backend-cr）
4. SQL/表结构变更联动 sql-review / db-schema-review 技能
5. 输出分级意见（引用文件:行号，说清触发条件与后果）
6. 评审人只报 >80% 把握的问题；风格问题交给工具，不占用人审
```

## 6. 评审礼仪

- 【推荐】对事不对人：意见针对代码与场景，不评价人
- 【推荐】提出问题时给出建议方案或依据的规范条目
- 【推荐】作者对每条意见必须回应：采纳 / 说明不采纳的理由（不沉默略过）
- 【推荐】争议升级：两轮未达成一致，拉技术负责人裁决，裁决记录进 MR

## 7. AI 辅助评审

- 【推荐】使用本仓库 `agents/` 下的评审子代理做第一轮筛查（code-reviewer / database-reviewer / security-reviewer），人工负责确认与最终决定
- 【强制】AI 意见未经人工确认不得自动合入；BLOCKER 级结论必须人工复核
