# 测试驱动开发工作流（TDD）

先写测试，看它失败，再写最小实现让它通过。

**核心原则：没看过测试失败，你就不知道它测的是不是对的东西。**
**遵守规则的字面 = 违反规则的精神——跳步骤的"走了流程"不算 TDD。**

## When to Activate

**必须使用**：新功能、bug 修复、重构、行为变更。

**例外（需人类伙伴确认）**：一次性原型、生成的代码、纯配置文件。

想着"就这次跳过 TDD"？停。那是自我合理化。

## 铁律

```
没有先失败的测试，就没有生产代码
```

先写了实现再补测试？先停止继续实现，保留并标记当前工作（不要删除未提交代码），回到测试设计并验证 RED。若确需重做，使用可恢复的提交、分支或 worktree，再从测试出发实现；不要把已有实现当成测试依据。

## RED-GREEN-REFACTOR 循环

### RED — 写一个失败的测试

写一个最小测试表达"应该发生什么"。

**要求**：一个行为、名字说清行为、测真实代码（能不 mock 就不 mock）。

好/坏对比：

```
✅ test_rejects_empty_email           —— 名字即行为，测真实路径
❌ test_retry_works                   —— 名字含糊，断言的是 mock 被调几次
```

写测试体之前先回答：**哪个生产代码变更会让这个测试失败？**（答不出来就重新设计——这是"为破坏点命名"原则，防止断言照抄实现）

### 验证 RED — 看着它失败（禁止跳过）

```
Java:   mvn test -Dtest=OrderServiceTest#rejectsEmptyEmail
Python: pytest tests/test_order_service.py::test_rejects_empty_email -x
```

确认三件事：
- 测试是**失败**（fail），不是**报错**（error/编译错）
- 失败信息正是预期的断言
- 失败原因是"功能不存在"，不是手误

测试直接通过了？说明在测既有行为，改测试。测试报错？修到"正确地失败"为止。

### GREEN — 写最小实现

写**刚好让测试通过**的最简代码。不加花活、不顺手重构、不"顺手改进"。测试之外的参数化、抽象、配置项都是 YAGNI。

### 验证 GREEN — 看着它通过（必须跑全量）

先跑目标测试确认通过，**然后跑项目全量测试**（`mvn test` / `pytest`）：

- 目标测试过了但别的测试挂了 → 现在就修
- 全量绿了才算 GREEN；只看自己那个文件绿就宣布完成 = 造假
- 自己没弄挂但确实红着的测试，必须在报告中点名——看着它滚过去而不提，就是漏报

### REFACTOR — 清理（只在绿灯后）

去重复、改善命名、提取辅助函数。**不加行为**，随时保持全绿。

### 重复

下一个行为，下一个失败的测试。

## 常见借口对照

| 借口 | 现实 |
|---|---|
| "太简单不用测" | 简单代码也会坏。测试只要 30 秒 |
| "写完再补测试" | 事后测试一跑就过——什么都没证明。你没看过它失败，就没证明它能抓 bug |
| "事后测试目的一样" | 事后测试回答"它做了什么"，事前测试回答"它该做什么"。实现后写测试会被已有代码带偏 |
| "我已经手工测过" | 手工测无记录、不可重放、有压力就漏。自动化每次都一样 |
| "删掉 X 小时的工作太浪费" | 不要丢失工作：先保存到可恢复的提交或分支，再回到测试验证行为 |
| "留着当参考，测试先写" | 先隔离并标记已有实现，测试必须从需求和行为出发，不能照着实现写 |
| "得先探索一下" | 可以。探索完成后保留可恢复记录，回到 TDD 重新开始 |
| "测试难写 = 设计不清楚" | 听测试的。难测 = 难用，简化设计 |
| "TDD 太慢" | TDD 才是务实路径：bug 挡在提交前，重构不心虚。"务实"的捷径 = 在生产环境调试 |

## 红旗（见到就停下重来）

- 先写了实现再写测试
- 测试一跑就通过
- 说不出测试为什么失败/该为什么失败
- "测试稍后补"
- "就这次不一样"
- "留着当参考"

**以上任何一条 = 停止继续实现，记录当前 diff，回到测试并重新验证；不要删除或丢失已有工作。**

## Bug 修复流程

发现 bug → 先写复现该 bug 的失败测试 → 走完整循环。测试证明修复有效并防止回归。**没有测试不修 bug。**

## 完成前检查

- [ ] 每个新函数/方法都有测试
- [ ] 亲眼看每个测试失败过（且失败原因正确：功能缺失，非手误）
- [ ] 每个测试都说得出"哪个生产变更会让它失败"
- [ ] 实现是最小实现
- [ ] 全量测试通过（不只自己的文件）
- [ ] 断言真实行为而非 mock 行为
- [ ] 边界与错误路径已覆盖

有勾不上的？跳了 TDD，保留当前可恢复工作并回到 RED 重新验证。

## 卡住了怎么办

| 问题 | 解法 |
|---|---|
| 不知道怎么测 | 先写"wished-for API"（理想中最顺手的调用方式），从断言倒推 |
| 测试太复杂 | 设计太复杂，简化接口 |
| 必须 mock 一切 | 耦合太重，上依赖注入 |
| 测试准备代码巨大 | 提取 fixture/helper；还大就简化设计 |
